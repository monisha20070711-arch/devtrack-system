1. Project Overview

DevTrack System is a full-stack SaaS issue and task management web application designed for modern software development teams. The word DevTrack combines "Developer" and "Tracking", symbolizing continuous oversight of software bugs, feature requests, and system improvements across their entire lifecycle.

The primary purpose of DevTrack is to provide a single, centralized web dashboard where project managers, software engineers, and QA testers can create issues, assign tasks to specific developers, monitor status transitions (Open → In Progress → Resolved), evaluate priority levels (Low, Medium, High), and analyze distribution metrics through visual charts.

30-Second Interview Overview Summary
"DevTrack is a production-style full-stack task and bug tracking web application. It features a modern Vanilla JS/HTML5/CSS3 frontend, a Node.js and Express REST API backend, JWT authentication with bcrypt password encryption, and a MySQL relational database for persistent task lifecycle management and real-time dashboard analytics."

2. Problem Statement

Software development teams frequently face significant communication gaps and project delays caused by fragmented bug tracking. In traditional workflows, issues are reported across scattered emails, chat messages, or unorganized spreadsheets.

This informal tracking introduces severe bottlenecks:

  • Lack of Centralization: Team members lose track of reported bugs and feature requests across separate channels.
  • Unassigned Responsibilities: Tasks lack assigned developer owners, leading to unaddressed critical defects.
  • Status Ambiguity: Managers cannot quickly ascertain whether a high-priority bug is actively being fixed, pending review, or resolved.
  • No Real-Time Visibility: Absence of visual metric distribution charts makes workload planning difficult.
Official Problem Statement
"Modern software projects require a centralized, secure, and real-time issue tracking system to eliminate unassigned bug backlogs, streamline developer assignment, enforce status transition visibility, and provide metrics-driven dashboard analytics for engineering teams."

10. Frontend Complete Explanation

The frontend is a lightweight Single Page Application (SPA) built without heavy third-party framework overhead. It operates dynamically by switching panel visibility within index.html based on state managed in app.js.

  • `config.js`: Dynamically computes API_BASE_URL as ${window.location.origin}/api, ensuring seamless operation locally or on cloud servers.
  • `api.js`: Handles HTTP GET, POST, PUT, DELETE requests. Automatically attaches Authorization: Bearer <token> and handles 401 unauthorized session expiration.
  • `auth.js`: Manages login/register tab switching, token persistence in localStorage, and profile rendering.
  • `issues.js`: Manages table rendering, developer dropdown population, modal form submission, live debounced search, multi-select filters, and delete confirmation dialogs.
  • `charts.js`: Interacts with Canvas elements to draw Donut and Bar charts representing Status and Priority distributions.

11. Backend Complete Explanation

The backend is built with Node.js and Express.js using the Model-View-Controller (MVC) architectural pattern:

  • `server.js`: Entry point. Configures CORS, JSON parsing, static serving of `/frontend`, mounts API routes under `/api`, handles 404/500 errors, and listens on `0.0.0.0:PORT`.
  • `config/db.js`: Manages MySQL connection pool (`mysql2/promise`). Tests connection on startup, creates missing tables automatically, seeds sample data, and provides mock fallback if MySQL service is offline.
  • `middleware/authMiddleware.js`: Intercepts protected requests, extracts JWT from the `Authorization` header, verifies validity using `JWT_SECRET`, and attaches decoded user payload to `req.user`.
  • `models/issueModel.js`: Executes SQL queries with parameterized inputs (`?`) to prevent SQL injection. Performs SQL `LEFT JOIN` on `users` table twice (for reporter and assignee names/avatars).

│     created_at  TIMESTAMP              │     └─► FK  reporter_id INT REFERENCES users(id) │
└────────────────────────────────────────┘       ├─► FK  assignee_id INT REFERENCES users(id) │
                                                 │     created_at  TIMESTAMP              │
                                                 │     updated_at  TIMESTAMP              │
                                                 └────────────────────────────────────────┘

SQL JOIN Query Example from `issueModel.js`

SELECT 
  i.id, i.title, i.description, i.status, i.priority, i.category,
  i.reporter_id, i.assignee_id, i.created_at, i.updated_at,
  r.name as reporter_name, r.email as reporter_email,
  a.name as assignee_name, a.email as assignee_email, a.avatar_url as assignee_avatar
FROM issues i
LEFT JOIN users r ON i.reporter_id = r.id
LEFT JOIN users a ON i.assignee_id = a.id
WHERE 1=1 AND i.status = ?
ORDER BY i.created_at DESC;

14. Authentication & Security

DevTrack implements stateless authentication via JSON Web Tokens (JWT):

  1. Registration: User submits credentials. Backend generates a 10-round salted bcrypt hash using bcrypt.hash(password, 10) and stores it in MySQL.
  2. Login Authentication: Backend retrieves user by email and compares entered password using bcrypt.compare().
  3. Token Generation: Upon verification, backend signs a JWT payload containing { id, email, name, role } using JWT_SECRET valid for 7 days.
  4. Protected Requests: Client stores token in localStorage and attaches it to request headers as Authorization: Bearer <token>.
  5. Verification Middleware: authMiddleware.js verifies token validity before passing control to API controllers.

18. Error Handling & Validation

  • Input Validation: Backend checks for missing required fields (e.g. title, email, password) and returns HTTP 400 Bad Request.
  • Duplicate Email Prevention: Returns HTTP 409 Conflict if email exists during registration.
  • Auth Failures: Invalid credentials return HTTP 401 Unauthorized with detailed message.
  • Global Express Error Middleware (`errorMiddleware.js`): Catches unexpected exceptions, logs stack traces in development, and returns structured envelope `{ success: false, message: "" }`.
  • User-Facing Feedback: Frontend displays animated green/red toast notifications for all operations.

23. Deployment Troubleshooting

31. Common Technical Interview Q&A (30 Questions)

Q1: Why did you choose Node.js and Express for DevTrack?
Node.js provides an asynchronous, event-driven runtime ideal for non-blocking I/O operations. Express provides a lightweight middleware framework for mapping REST API endpoints cleanly using MVC pattern.
Q2: How does authentication work in your application?
When a user logs in, backend verifies password using bcrypt.compare(). If valid, it signs a JWT token containing user metadata and returns it to the client. The client stores it in localStorage and includes it in request headers as Authorization: Bearer <token>.
Q3: How do you prevent SQL Injection vulnerabilities?
All SQL queries in issueModel.js and userModel.js use parameterized placeholders (?) with mysql2/promise, ensuring user input is sanitized before query execution.
Q4: How do SQL JOIN queries improve database efficiency in DevTrack?
Using LEFT JOIN on users twice allows us to retrieve issue metadata, reporter name, and assignee name/avatar in a single database query, avoiding N+1 query performance problems.
Q5: What is the purpose of connection pooling in db.js?
Connection pooling reuses database connection instances rather than creating and destroying a new database connection for every incoming HTTP request, significantly reducing database connection overhead.

32. Difficult Technical Interview Questions

Q: How would you scale DevTrack to handle 100,000 concurrent users?
Confident Answer: I would introduce horizontal scaling by deploying multiple Express server instances behind a Load Balancer (such as NGINX or AWS ALB). Since our JWT authentication is stateless, any server instance can validate requests. For the database, I would introduce Redis caching for dashboard stats and implement MySQL read replicas.
Q: What happens if the JWT secret key is compromised?
Confident Answer: If the key is compromised, attackers can forge valid tokens. To mitigate this, we would immediately rotate `JWT_SECRET` in environment variables, invalidating all existing tokens and requiring users to log in again.
